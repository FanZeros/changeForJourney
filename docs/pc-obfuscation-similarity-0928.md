# L1 混淆效果 · 发布包源码相似度实测

> 工具：`FanZeros/tempGame` 的 `skills/source-similarity/scripts/compare_lua_similarity.py`
> （比对 Maker 发布包 `<uuid>-<hash>.lua` 资产与本地 `scripts/` 源码树，按行 difflib
> SequenceMatcher 算加权相似度；`read_text` 对 `\x1bLua` 字节码头返回 None 单列为 bytecode）。
> 方法：同一套源码分别构建「未混淆发布包」与「L1 混淆发布包」，各自与该源码树对比。
> 下文文件计数为实测快照的数字，随代码增长会变化，比例结论稳定。

## 结论：L1 混淆把「发布包=源码」的逐字节泄露，降到行级相似 46%、逐字节行占比 2.8%

| 指标 | 基线（未混淆包 vs 源码） | L1 混淆包 vs 源码 |
|------|------------------------|-------------------|
| 对称相似度 symmetric_dice | **100.0%** | **46.0%** |
| 发布包被源码覆盖率 | 100.0% | 46.0% |
| 配对文件加权相似度 | 100.0% | 46.0% |
| **发布包逐字节行占比** | **100.0%** | **2.8%** |
| 完全一致文件数 / 361 | **361** | **17** |
| project_id / 行数 | m_7b83 / 135887 | m_7b83 / 135887 |

**怎么读这张表**：
- **基线 100%**：未混淆发布包与源码逐字节相同（361/361 exact）——明文发布，拖出来就是源码。
- **混淆后逐字节行占比仅 2.8%**：97.2% 的行相对源码发生了改动（几乎每个含
  local/参数的行都因改名而变），发布包里再也找不到成片的原始源码文本。
- **混淆后行级相似 46%**：剩下的相似度来自**未改名的部分**——注释、字符串、
  字段名/方法名、`require` 路径、排版空行（L1 刻意保留这些以保证可运行与
  过官方 LSP）。这是「保守重命名」档的预期天花板：它去掉变量名语义，但
  不删注释、不改控制流，故行结构仍可比对。

**混淆后 exact 的 17 个文件** = 16 个纯数据表（StageConfig_*/AssetManifest，
无 local 绑定可改）+ `core/DarkIcon.lua`（luaparser 中文 token 解析失败被安全
跳过，仍明文）。这 17 个是 L1 的已知盲区。

|------|------|--------|------|
| ui | 128 | 41.3% | 逻辑密集，改名收益最大 |
| systems | 51 | 42.4% | 同上 |

### 最发散文件（混淆后相似度最低）
`core/I18nDict.lua` 0.3%、`core/I18nDictExtra.lua` 7.2%、多个 `tests/*` 17-23%
——这些是超长字典/测试，局部变量极多，改名后与源码几乎无共同行。

## 进一步降低相似度的可选手段
46% 的残留主要来自**注释 + 字符串 + 对外字段名**。可选叠加（详见 `docs/pc-protection-research-0927.md`）：
1. **L2 字节码**：`compare_lua_similarity.py` 对字节码文件直接判 `kind=bytecode`
   （不计入行相似），一旦发布包是 `.luac`，行级相似度指标失去意义——这是把
   「46% 行相似」变成「0 可读行」的根本手段。**但 WASM VM 是否接受字节码仍待
   在真实打包环境验证**，见 `electron-shell/WINDOWS_PROTECT_CHECKLIST.md`。
2. **发布版剥离注释**：Build 后、打包前对 dist 侧再去注释会破坏 manifest hash；
   正确做法是在混淆工作区生成阶段就产出「无注释版」，但这与官方 LSP 的 EmmyLua
   依赖冲突，需权衡。
3. **L1 增强**：字符串字面量提取+运行期解码（中档），可再降字符串贡献的相似度。

**当前保守 L1 已把逐字节泄露（100%→2.8%）消除**；行级相似 46% 是「保留可运行性
+ 过官方 LSP」的代价，要归零须靠 L2 字节码。
