### 4.6 逐项用途详解：玩法、配置与数据结构的区别

以下按实际本地源码解释上述62项，不重新计算相似度，也不把“存在某文件”当成它必然被当前启动链调用的证据。当前项目为单机版，遗留协议和跨服档案字段的存在不意味着正在联网。

先区分三类职责：

- **数值配置**：回答“有哪些关卡、怪物、奖励，数值是多少”。例如挂机收益表不直接发奖励。
- **玩法运行时**：回答“发生攻击、抽卡、挂机等操作时，怎样计算并改变状态”。例如战斗公式计算伤害，神器运行时响应战斗事件。
- **存档结构与兼容**：回答“哪些数据需要保存，旧存档怎么补齐”。`Schema`通常注册字段和默认值，不等于实现抽卡、签到或战斗结算；`Compat`负责旧数据迁移。

此外还有事件、音频、数值显示、状态代理、调试诊断和类型声明等支撑模块。每项说明对应 `scripts/` 下的本地文件，功能核查为静态读取，不冒充运行时覆盖或完整安全审计。

## 5. 工具算法与统计局限

1. **读取与规范化**：文本按 UTF-8 解码；CRLF 和 CR 统一为 LF；不能解码的字节用替代字符；Lua 字节码跳过。行级比较去掉每行尾部空白，不去注释、不替换变量名、不做 AST 或 token 分析。
2. **同路径相似度**：只比较同一相对路径的两份文件，用 `difflib.SequenceMatcher(..., autojunk=False).ratio()`，记作 `s`。配对权重为 `max(镜像行数, 本地行数, 1)`，再求加权平均。去空行指标按非空行重新比较与加权。
3. **全量双向指标**：每侧文件行数乘以其同路径相似度，未配对路径按 0 计；两侧估算匹配行数之和除以两侧总可读行数，形成 `symmetric_dice`。这不是标准 token 集合 Dice，也不是实际相同行数精确计数。
4. **完整文本相同**：先统一换行，再以 SHA-256 判断；这里没有去尾空格、去注释或去空行。跨路径整文件哈希匹配只进入 `exact_line_pct_*`，**不会提高同路径覆盖率或双向相似度**。
5. **路径重构影响**：搬移、改名、模块拆分、模块合并可能使实际相关代码被统计为两侧独有路径；例如镜像 `ui/RewardPopup.lua` 与本地 `ui/hud/popup/RewardPopup.lua`，工具不自动比较。
6. **缺失文件影响**：《灰界》只读取到 48 / 241 个 Lua，193 个缺失清单项包括 `LuaScripts/` 71 项、`urhox-libs/` 112 项、`Validate/` 7 项及根目录库文件 3 项，不能统称为业务源码缺失；唯一同路径配对为 `main.lua`。缺失项不参与可读行数总量，路径集合仍含缺失条目，路径重合的分母与内容分母不完全一致。原报告的 `only_published` 不等于仅“已读取且本地缺少”的文件名单。缺失内容未知，不能确定它们对完整相似度的净影响方向。
7. **口径包含测试和配置**：本地含测试、工具与配置，配置格式化、注释、空白和大量新增测试都可能影响结果；镜像 manifest 也可能带入示例或工具路径。不能据文件数量直接推断玩法规模。
8. **结果不具法律定性**：相似代码可能源于同项目历史版本、授权复用或公共模式。报告只提供技术比较结果，不能据此判定抄袭、侵权或代码作者归属。

#### 通用底座保留与替换原则

- **不能把高相似文件都当成竖屏UI。** 配置、公式、存档结构和通用工具要分别判断；直接绘制、输入、窗口尺寸和数据操作的耦合应拆开。
- **不能把有旧字段当成旧功能仍在运行。** 看当前启动及静态调用链，区分主流程使用、特定条件使用、兼容注册及未找到接入。
- **原创性的重点是玩家决策与规则。** 不靠换皮、改文件名、移动目录或格式化降低相似度；保留可靠通用底座，把核心目标、操作、战场规则、构筑和奖励循环做出区别。
- **玩法迭代不等于清空玩家资产。** 新规则应有版本化状态、兼容导入及回滚隔离，保留已拥有角色、装备、货币和旧进度的处理协议；不可无迁移删除旧键。
- **先做可玩的新机制小闭环。** 比一次重写关卡、UI、经济和存档风险更低；每阶段有测试与真实画面验收，再扩大范围。

### 9.3 建议的原创玩法方向（待用户选择）

推荐先做 **“横屏指令战术＋路线探索”** 的最小样板，不立即把全部旧系统重写：

1. **战前可读情报**：展示敌人下一次行动意图、目标及危险区域，玩家能因信息改变部署，而不是只看战力数。
2. **有限指令资源**：单位保留基础自动攻击，玩家用共享指令点在关键时机执行集火、守护或换位；指令成本和冷却形成取舍，不能所有按钮同时无脑释放。
3. **非纯清怪目标**：同一战斗引入守点、护送或打断蓄力的目标，失败原因不只有数值不足。目标判定应独立于伤害公式和UI。
4. **战后路线与构筑选择**：先用短路线的奖励、事件、恢复节点验证取舍，提供战斗内可感知的能力选择；不是继续无限堆属性或把随机抽卡作为唯一成长来源。

这些是建议而非已确认规则：最终需要确定实时指令、战术暂停或回合制中的一种节奏，以及队伍人数、单局时长、站位自由度和旧资产导入方式。第一阶段建议只选3名可用单位、3类敌人、2类目标和一段短路线，避免同时加入大地图、多套卡池及完整经济。

### 9.5 实施前的拆分与迁移清单

**先解除3处隐性耦合，不先全盘换UI或战斗：**

**UI逐页顺序：** 新战斗HUD和普通副本混合坐标 → 角色/详情 → 背包/锻炉联动 → 城镇与建筑 → 通用弹窗及过场。新菜单、HUD、列表、按钮使用 `urhox-libs/UI` 组件并检查对应主题，默认DPR自适应和安全区；战场特殊绘制可保留raw NanoVG，但与UI输入和层级协调。每页同步迁draw、hit、滚动、拖拽、教程热点与动画，旧兼容适配器暂保留。

**新存档不能仅将version改成2覆盖旧文件。** 当前 `StandaloneSave` 写version=1，但恢复只检查table/modules，不校验版本，旧程序会误读新结构。应使用独立v2文件/槽位，明确 `gameplayId`、`gameplayVersion`、`saveFormatVersion`，旧 `standalone_save.json` 原字节备份保持不变；完成写出、回读、资产校验后才切新入口。依据：`scripts/boot/StandaloneSave.lua:26-27`、`:55-73`、`:137-150`。

迁移必须保留或明确映射：

- GameState与modules的双源余额、等级和经验；先验证一致性，不任选一份丢弃。
- 英雄ID、roster编码、deployed到teams、觉醒及碎片转换标志；装备实例ID、inventory/equipped/nextSeq和水合派生字段。

- 任务奖励迁移、签到、兑换码、特权权益、保底、神器装配等领取与资产记录；新玩法不消费的旧信息封存legacy包而非删除。

迁移流程为：旧档只读备份 → 隔离副本归一化 → 映射新ID及状态 → 校验资产/关联/账本 → 写v2并回读 → 切入口。记录迁移来源摘要和完成标志，幂等执行；失败不覆盖旧档。回滚默认恢复迁移前v1快照，不让旧读取器直接吃v2，也不承诺未经设计的v2新增资产自动回写v1。

### 10.5 后续调整的分层方式

- **参数层**：同一规则下调整概率、上限、收益曲线、节奏和奖励成本，先用代表关卡及队伍验证。
- **规则层**：改变重复英雄价值、保底计数、仇恨分配、共鸣约束、词缀组合等决策关系，不必改变自动战斗主形式。
- **系统层**：重新定位三队推进、塔内强化和长期成长的关系，减少重复刷同质内容，保留已有角色及装备数据的迁移契约。

每个调整都需要写出具体目标（例如降低重复劳动、增加阵容差异、缩短卡关等待），并定义对照指标；不为了让数字更低而改名、搬文件或格式化。优先小批规则实验，再扩大到系统，保持现版已有改动及已验证体验。

### 10.6 对照后如何推进，而不是推倒重来

1. 先确认两侧规则的差异和实际调用，区分已修改、仍共享、代码保留但当前模式未采用。
2. 从用户最在意的体验挑一组设定，例如盾/暴击、共鸣/重复英雄、挂机/掉落或塔强化，不同时修改全部系统。
3. 为选中组写出参数方案或规则方案及其影响，记录当前基线、目标、代表角色/关卡和预期边界；未经用户选择不直接改变规则。
4. 验证改动不会抵消现版已有优化、造成奖励重复、影响旧资产或破坏三队；通过后再扩展更多配置。

方案选择看实际问题而非相似率：若角色定位不明显，调技能与阵容联动；若卡关靠等待，调收益/升级/敌人曲线；若装备组合单一，调词缀和收益边际；若塔内选择同质，调强化互斥、触发和组合。保持自动战斗与已有横屏三队也可以做出差异，不必先选手动指令路线。
