## 一、审计方法

从入口 `scripts/main.lua` 出发构建 require 依赖图，BFS 求可达集。依赖识别覆盖四种形式，避免漏判动态加载：

1. `require("dotted.path")` —— 常规静态引用
2. `pcall(require, "dotted.path")` —— `runtime/LocalActionBridge.lua` 用此形式动态加载全部 `rules/*Handler`
3. 字符串常量中出现的完整模块名 —— 如 `LocalActionBridge` 的 `packs` 表（`{ "rules.battle.BattleHandler", ... }`）
4. `ui/ModuleMap.lua` 的 `resolve()` 动态 require —— MAP 全条目视为依赖

**结果**：全仓 378 个 Lua 模块（不含 `.d.lua`），从 `main.lua` 可达 328 个，不可达 50 个。
其中 `tests/`(28) 与 `_proc/`(18) 是外部运行的测试与离线工具，不可达属预期；
**正式游戏代码不可达仅 4 个**（AssetManifest / SaveManager / VersionConfig / DamageGlyph）。
`UpdateNoticePopup` 经 ModuleMap 字符串可达，但 ModuleMap 的唯一消费点是开发钩子，故实际游戏内无法进入。

复现脚本见 `.tmp/audit_graph.py`（依赖图）、`.tmp/audit_modulemap.py`（ModuleMap 可达性），未入库。

## 三、逐一证据

### 1. DamageGlyph.lua —— 程序化伤害字形图标，死代码
- 全仓 `grep DamageGlyph`（含注释）仅命中自身文件，零外部引用。
- `ui/battle/fx/` 目录只有 `DamageGlyph.lua` + `.meta`，是孤立目录。
- 文件实现了一套按伤害类型（撕咬/斩击等）程序化绘制矢量字形的 `GLYPHS` 表，但战斗飘字走的是文本描边实现（`BattleCombatFx` 等），从未调用这套字形。
- 判定：完整实现但全仓零接入 → 死代码。

### 2. SaveManager.lua —— 单机 stub，死代码
- 所有方法为空实现或仅 `print`：`register/registerFromRegistry/markDirty/savePlayerNow/update/cleanup` 全空，`load/loadGlobalProfile` 仅 print 后回调 `true`，`getTable/getAllTables` 返回 `nil`。
- 文件头注释：「云存档已删除……仍保留 load/flush 等旧入口，全部改为本地空操作，避免残留调用再走云」——但全仓零 require，说明"残留调用"已不存在。
- 判定：为兼容旧云存档调用而保留的 stub，调用方已清空 → 死代码。

### 3. VersionConfig.lua —— 版本号配置，死配置
- 全仓零引用（仅自身文件）。
- `VersionConfig.CURRENT = "1.0.39"`，而 `.project/project.json` 的 `version = "1.0.7"`，两者不一致且无人读取 → 证明该配置从未生效。
- 判定：死配置。

### 4. AssetManifest.lua —— 全量图片清单，死配置（新增发现）
- 文件头注释：「自动生成：全量图片清单（一次性加载用，带文件字节数）」。
- 全仓零 `require` / 零 `dofile` / 零 `loadfile`；`tools/`、`maker-mcp/`、`.project/`、所有 `.py`/`.json`/`.meta` 均无引用。
- `boot/Standalone.lua:422` 仅有一句 `print("[Standalone] skip full AssetManifest DWP wait")` 提及（说明启动时**跳过**了基于它的全量下载）。
- `.meta` 仅含 uuid，非构建引用标记。
- 判定：运行时死配置（详见第四节构建引用澄清）。

### 5. UpdateNoticePopup.lua —— 功能未接线，游戏内无法弹出
- 实现完整：含遮罩/面板/标题/内容/「我知道了」按钮，设计分辨率 1080×2400。
- 文件头注释写明用途：「当检测到 `nvgSpineCreate` 不可用时弹出，提醒玩家更新 TapTap 客户端」。
- 唯一挂载点：`ui/ModuleMap.lua:125` `["UpdateNoticePopup"] = "ui.hud.popup.UpdateNoticePopup"`。
- ModuleMap 的唯一消费点：`boot/Standalone.lua:1007`，且被 `if H_AUTO_OPEN_PANEL and H_skipDone ...` 包裹——`H_AUTO_OPEN_PANEL` 是仅 `_validate_entry.lua`（B3/B5 截图验收）置位的**开发钩子**。
- 全仓搜索 `nvgSpineCreate` 的可用性检测：无任何代码在 spine 创建失败时调用 `UpdateNoticePopup.show()`。设计意图与实现**未接线**。
- 判定：非纯死代码，而是"功能完整但未接入触发点"。游戏内（非 dev 钩子）永远无法弹出。

## 四、关键澄清：AssetManifest 与构建引用模式

`docs/memory-index.md` 历史记录对 AssetManifest 定性**矛盾**：
- 一处称「AssetManifest 实为死配置，全仓无 require/dofile 加载它」；
- 另一处称「构建自动生成的资源清单……如需彻底移除资源需删图+重建 manifest」，并警告删除 `UI_JTSQ_BJ.png` 条目时「AssetManifest 清单条目与 png 文件本身都不能删」。

**本轮用 `.project/resources.json` 澄清**：

```jsonc
{ "preload_groups": [], "groups": { "default": ["**"] } }
```

`groups.default = ["**"]` 是独立 `**` 条目 → 据 `engine-docs/recipes/preload-and-build-refs.md`，本项目为**全量引用模式**：所有本地资源直接入包，**不追踪引用链、不依赖 AssetManifest**。

结论：
- AssetManifest 在运行时是死配置（无人 require）。
- 删除它**不影响图片打包**（全量引用模式下 png 靠 `**` 入包，与 AssetManifest 无关）。
- memory-index 中"不能删 AssetManifest 条目"的警告，针对的是**未来若切换到增强引用模式**的场景；当前全量引用模式下该顾虑不成立。
