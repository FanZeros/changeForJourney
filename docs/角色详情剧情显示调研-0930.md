# 调研报告：为什么点击角色详情一直会显示剧情（2026-09-30）

## 结论速览

点击角色详情触发剧情的入口**只有一个**：`CharacterDetail.open()` / `CharacterDetail._switchHero()` → `HeroScenario.onOpenHero(heroId)`，且**仅对四个玩梗角色生效**（18 老六 / 19 哈基米 / 24 加载中 / 25 高ping战士，见 `HeroScenario.lua` 的 `JOIN_ID`/`IDLE_ID` 表）。其他角色点详情**不会**走这条链。

"一直会显示"的根因是**闲聊剧情（78–81）按设计每局进程播一次、不落档**：

- `HeroScenario.lua` 顶部的 `idleSeen_` 是**纯内存表**（module 级 local），进程重启即清空；
- 文件头注释与 `docs/剧情总表.md` 均写明："入队只播一次（写入 session.claimedScenarios）；**闲聊每次进游戏每个角色播一次**"；
- 开发阶段每次 build/预览/刷新都是新进程 → 每次重启后第一次点这四个角色的详情必然弹闲聊剧情，体感就是"一直会显示"。

## 完整触发链

```
CharacterInput.lua:134/178/189（点头像编队槽 / 点角色卡）
  → CharacterDetail.open(heroId)                     detail/CharacterDetail.lua:361
  → CharacterDetail._switchHero（左右滑卡切人，keepDrag=false 时）  CharacterDetail.lua:438
      → HeroScenario.onOpenHero(hid)                 hero/HeroScenario.lua:216
          ├─ 未拥有 → 直接 return（不播）
          ├─ playJoinThenIdle:
          │    入队剧情 74–77：isClaimed(joinId) 或已拥有(owned.level) → 跳过并补 markClaimed
          │    未看过且未拥有过 → showScenario(joinId)，成功后 markClaimed（落档 claimedScenarios + StandaloneSave.Flush）
          └─ playIdle:
               闲聊 78–81：仅查内存 idleSeen_[heroId]，没看过就播 —— 不落档，重启必重播
```

另有两条入口播同一套入队/闲聊：
- 招募出新人：`TavernPage.lua:625/1321` → `HeroScenario.onRecruitResults`
- 碎片合成成功弹窗关闭：`ClientMessageHandler.lua:602` → `onOpenHero`

## 为什么"每次点"都可能出现（同进程内的次生路径）

1. **pending_ 延迟补播**：`showScenario` 时若已有对话在播（`ScenarioDialogue.isActive()`）会返回 false → `enqueue(heroId)` 进 `pending_`。但 `pending_` **只在** 下一次 `onOpenHero` / `onRecruitResults` / 某个 HeroScenario 自己的 onFinish 里被 `drainPending()` 消化——`ScenarioDialogue` 正常播完（如城镇剧情 23–26）并不会通知 HeroScenario。结果：玩家下一次点详情时，积压的闲聊/入队突然补播，体感"每点一次弹一次"。
2. **左右滑卡也触发**：`_switchHero` 松手落定（keepDrag=false）也会调 `onOpenHero`，连续翻四个玩梗角色会各弹一次（每角色每进程一次的额度各自独立）。
3. **join 后自动接闲聊**：首次看入队剧情（74–77）时 onFinish 直接串播闲聊（78–81），一次点击连弹两段，加重"总是弹剧情"的感受。
4. **claimedScenarios 写档失败风险（已缓解）**：上一提交（4a152ca8）之前 `markClaimed` 的同步 `handleStateUpdate` 异常会中断流程；现已 pcall 保护，但失败时仅打印日志，入队剧情**跨进程重播**的可能性仍存在（日志关键字 `[HeroScenario] markClaimed state update failed`）。

## 排除项（确认与本问题无关）

- `StoryPlayer`（城镇 23 / 教堂 27–30 / 关卡首通等）：由 `Standalone.lua:955 tryPlayPendingStory_()` 每帧泵出，与"点详情"无因果，只是时间上可能撞车；这些 id 播后会写 `claimedScenarios` 落档，不会重复。
- `TutorialManager`：新手引导高亮期间反而**禁止**点详情（CharacterInput.lua:170 附近）。
- session 持久化链路本身正常：`markClaimed` → `handleStateUpdate` → `ModuleRegistry.onLoad`（数字 key 转字符串）→ `StandaloneSave.Flush`，`isClaimed` 同时查字符串/数字 key。

## 可选修复方向（待定，未实施）

| 方案 | 改动 | 效果 |
|------|------|------|
| A. 闲聊也落档 | `playIdle` 成功后同样 `markClaimed(idleId)`，`playIdle` 前查 `isClaimed` | 闲聊终身只播一次，最彻底 |
| B. 闲聊落 session 但独立字段 | 存 `session.idleSeen = {["18"]=true,...}`，与 claimedScenarios 分开 | 保留"claimed 语义只给奖励型情景"的整洁 |
| C. 保持每局一次，修 pending_ 补播 | `ScenarioDialogue` 结束时广播（或 Standalone.update 里检测 active→false 跳变）调用 `drainPending` | 不改设计，只消"延迟突然弹"的坏体感 |
| D. 关闭详情页闲聊入口 | `onOpenHero` 只处理入队，闲聊仅招募后播 | 点详情永远不弹闲聊 |

> 推荐 A/C 组合：闲聊改为落档一次（A），同时补上对话结束事件驱动 drainPending（C），彻底消除"点详情必弹剧情"与"延迟补播"两类现象。
