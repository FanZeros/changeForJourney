### 2.1 三个必须区分的历史

1. `claimedScenarios[id]`：旧剧情入口防重播，可能播放前预写，可能跳过；不是完整阅读。
2. `scenarioRewardsGranted[id]`：成功结算，纯对话也记账；不是完整阅读。
3. 新切片阅读结果：应明确 `finished / skipped / 未完成`；不要迁移旧claimed为finished。

旧 `introCompleted` 也在开场开始时写入。因此新内容除了检查该字段，还必须等真实开场流程、标题、来信和当前对话结束。

## 3. 新节点触发与依赖

### 3.1 普通104日志夹页

实时流程：

```text
104首通 → 现有首通进度落盘/奖励
  → 旧17/18/19按既有队列播放或跳过
  → 旧待播剧情/FOLLOW继续按原顺序消化
  → 教程/奖励/离线/其他模态空闲
  → 新N02（无奖）→ E01加入档案
```

**“在旧段之后”是依赖，不保证紧贴。**为了不抢旧FOLLOW或并发剧情，新节点允许在旧队列消化后出现，中间可隔原有情景。首批不建立全局插队机制。

处理旧段：

- 本进程刚播17/18/19：自然结束或用户skip均释放依赖，记录是 `live_finished` 或 `live_skipped`。
- 旧段未claimed且104已通：先按现有backfill排旧段，新N02等旧播放源为空后再播。
- 旧段claimed但无真实完成记录：接受“旧防重播记录存在”的迁移事实作为**不强制补播**条件，来源为 `legacy_claimed_unknown`；不写“已完整读过”。N02本身重新建立短语境。
- 无效/丢失旧配置：新层不得永久等不存在的段，记录迁移警告并允许独立无奖补读；实现时不要把该异常静默当读完。

### 3.2 噩梦4905征用核验

资格必须来自 **`clearedStages[4905] == true`（兼容数字/字符串键）** 或本进程已确认的成功首通事件。`maxStageId>=4905`、当前关为4905、打开过地图均不单独证明通关。

三节点按固定顺序：`cargo_match → gray_order → people_record`。前一节点自然结束或显式skip才释放下一节点；reset、重启中断、错误不释放。

旧70–73为语境参考，不是新节点永久门槛：

- 实时新档的70–73已按原进入事件入队。播放仲裁先消化旧内容，自然在新核验前出现。
- 旧档4905已通但缺73：现有backfill不会补ENTER；**不强迫补播73、不把旧claimed写成已读**。
- 新N12–N14可凭铁匠案件资料自成核验，不需要玩家先看新N11。初始提示只说“铁匠请核对一张旧货牌”，不得替玩家宣布其梦见过什么。
- 最小切片采用明确的语境适配：N12按 `player_record/case_archive`显示“你带来的货牌”或“铁匠保存的货牌副本”；不能写玩家未必经历的新N03。
- N14新增狗台词改用“叫……被征用的不只是箱子，还有护送的人？”，不引用其未必听过的旧72“送走”。这只调整新增切片用语，不改旧72原句；全篇N14可保留有上下文版本，两者在新配置明确选择。
- 原70–73允许在只读补读入口中查看完整原文，标注“原情景原文”，不发奖、不触发教程、不追加FOLLOW；未看补读不锁核验。

### 3.3 城镇调查是情景地点，不是操作门槛

N12舞台在城镇登记处，但不强迫玩家退出战斗、点教堂或等待具体建筑打开：

- 资格成立后提示有“待阅调查”；在安全空闲点使用横屏情景呈现登记台背景。
- 只改变展示地点，不改当前关、编队或建筑访问状态，不发送 `onPlace`。
- 需要新的背景/人物映射时单独确认；首批优先复用有效资源或纯底板，不能猜人物数字映射。

## 4. 唯一播放仲裁与无奖上下文

### 4.1 仲裁优先级

拟在既有 `tryPlayPendingStory_` 的尾部接窄范围分支：

1. 当前标题/来信/开场链/对话正在播放：不取新节点。
2. 现有奖励、离线、更新提示、重要模态、战斗结算或有效拖拽：新层等待。
3. 现有pending情景、pendingFOLLOW、StoryPlayer继续走原顺序。
4. 只有旧播放源真的没有可播项，且教程组不活跃，才尝试新节点/用户明确回看请求。

**不要提前调用新层的take。**新层使用 `peekReady` 非破坏性检查，所有门禁通过后 `begin`取得一次性展示租约。

旧 `StoryPlayer.take()`在原位置调用一次；返回nil是必要条件，**不是旧播放源全部清空的充分条件**。如果本轮先拿到无效pending情景，旧逻辑可能没有消费pendingFOLLOW；必须非破坏性确认两类pending槽都为空，才尝试新层。

建议ClientMessageHandler新增只读 `hasPendingScenarioDialogue/hasPendingFollowUpDialogue`候选API，或一个等价布尔查询，不改变旧consume分支。若还有未消费pending，本帧不启动新层，留给下一帧原逻辑处理；不增加第二次consume/take探测、不丢弃旧项。

### 4.2 展示租约（拟定）

每次新节点播放持有：

```text
kind = samsara_first_read | samsara_replay | legacy_reference
nodeKey = 字符串新节点键（legacy_reference另有sourceScenarioId）
contentVersion = 1
playToken = 本次进程唯一token
contextEpoch = 当前存档/会话代数
```

只有该租约对应的结束结果可以写入新进度。旧英雄闲聊、原剧情或重启后迟到回调都不能完成另一个节点。

租约不是存档中的“已经完成”标记。重启后旧token无效，只保存已处理节点结果。

### 4.3 新无奖分支的禁止事项

新切片播放结束、skip与回看：

- 不设置旧 `claimedScenarios`。
- 不调用 `setPendingTutorialNotify`。
- 不发送 `claim_scenario_reward`。
- 不写 `scenarioRewardsGranted`。
- 不调用旧 `followOf`。
- 不发奖励弹窗，不刷新经济/角色属性，不发建筑访问事件。

`replay=true/noReward=true`仅是设计字段，**现有代码不会自动理解**。必须有实际独立分支及测试spy证明上述调用为零。

## 5. 对话结束语义：有token、有reason、下一帧再播

### 5.1 推荐的窄扩展

为 `ScenarioDialogue.show`新增**可选且仅新分支使用**的结果上下文，例如：

```text
completionToken = { playToken, contextEpoch, nodeKey }
onResult(result)   -- result包含捕获的token和finished/dismissed/skipped
```

这里是拟定接口，不是引擎或现有项目API。旧 `onFinish`签名与旧完成广播保留，旧调用者不用改。

实现时在三条实际结束路径中加入仅针对新结果槽的短helper：

1. 捕获新结果槽的本次mode、token、result callback到局部变量。
2. 只清空新结果槽，保证同token最多回调一次；原active/旧onFinish清理位置保持。
3. 新结果使用捕获内容报告 `finished/dismissed/skipped`，不读取后来被其他show改写的身份。
4. 无新结果上下文时三条旧结束路径原样保留；不把捕获mode替代旧广播的全局mode，不提前清旧onFinish，不顺手改变旧同步链行为。
5. 新无奖分支不绑定领奖onFinish；onResult只记结果/排队，下一帧由仲裁器启动下一节点。

**重要边界**：现有结束路径会在回调后将全局onFinish置nil，回调内立即show可能丢失下一段回调。这是现有同步链风险。新节点必须下一帧由仲裁器启动，不能把它复制进新增链。可选结果helper不能借此全面改开场链；若共同helper碰到旧同步行为，先用回归验证兼容，再决定是否单独修复。

### 5.2 成功、跳过、中断

| 结果 | 新节点处理 | 后续依赖 | 证据 | 回看 |
|---|---|---|---|---|
| finished/dismissed | `resolution=finished` | 释放 | 固定解锁保留 | 可用 |
| skipped | `resolution=skipped` | 释放，不要求强读 | 固定解锁保留 | 可用，标“已跳过” |
| reset/清档 | 当前租约取消 | 不释放原存档中未完成节点；清档整体归零 | 按新档资格重新建立 | 不假称读完 |
| 普通退出/崩溃 | 不写成功 | 下次重新从该短节点开始 | 已按通关资格解锁者仍保留 | 可继续 |
| show失败/配置缺失 | 不写成功，保留待阅 | 不释放 | 不发奖，不丢原数据 | 提示重试 |
| token/epoch不符 | 忽略旧结果 | 不释放 | 不写入另一存档 | 不污染 |

skip是用户明确处理，不等于完整阅读。它必须避免卡链，又不能写成finished。

### 5.3 结束信号与任意旧剧情

旧 `scenario_dialogue_finished`没有scenarioId，不能单独凭它完成N02。新层只信 `onResult`捕获的token。

新结果发生后，`HeroScenario`等旧广播订阅者仍可能补播闲聊。仲裁器下一帧重看 `ScenarioDialogue.isActive()`；如果已被其他合法旧来源占用，新层继续等，不覆盖。

## 6. 状态模型与落盘

### 6.1 一个嵌套session字段

推荐在既有session内加入版本化 `samsaraStory`，不新增顶层业务模块：

```text
samsaraStory = {
  schemaVersion = 1,
  nodes = {
    [nodeKey] = {
      eligible = true,
      eligibilitySource = clear_104 | clear_4905 | live_clear,
      contentVersion = 1,
      resolution = finished | skipped | nil,
      legacyContext = live_finished | live_skipped | legacy_claimed_unknown | unavailable,
    }
  },
  evidence = {
    E01 = { unlocked = true, source = clear_104 },
    E02 = { unlocked = true, source = clear_204 | case_archive },
    E05 = { baseUnlocked = true, peopleAppendixUnlocked = true|nil },
  }
}
```

这是结构方案，不是本轮生成的存档。精确字段名在实现时统一，不把策划N编号写到旧scenario命名空间。

### 6.2 阅读与解锁分开

- E01资格由104已通建立，E02由204/案件副本建立，E05资格由4905建立；**资格只决定待阅，不直接公开尚未处理节点的正文/核验批注**。
- 未读显示“待阅”；点开走该节点首次阅读，跳过可回看，不永久缺证据。
- E02原件按204/案件副本规则开放，来源核验批注在N12处理后开放。
- E05初始抄件在N13处理后公开，续令与人员卷在N14处理后公开；N17及以后核验结果本批始终锁定。
- finished和skipped均算首次处理，但分别记录，不把skip写成完整读完。
- 本批不给E04、E06、E07或地狱批注解锁；它们不在这次切片范围内。
- `resolution`不用于经济结算，也不推导真实团灭历史。

### 6.3 Schema迁移

需要同时覆盖：

1. SessionSchema默认值创建新表（每个实例独立）。
2. SessionSchema.onLoad调用共享normalize。
3. ModuleRegistry的session onLoad也调用同一normalize，保留原claimed/granted规范化。
4. LocalActionBridge拿到已存在旧session时仍确保字段存在，不依赖默认值合并。
5. 未知未来schemaVersion不得静默清空；只读保留并禁用不兼容新展示，提示待升级。

normalize只修新字段的结构/键和值，保留所有其余session字段。不能整表只返回samsaraStory，否则教程、开场、离线次数和奖励账本丢失。

迁移验收分别调用SessionSchema和ModuleRegistry的onLoad，再连续normalize两次，断言幂等、旧字段保留、未知未来版本原样保留；不把同一次Dispatcher更新只经过一个onLoad当覆盖两路径。

### 6.4 实际写入与故障

写新进度时：读Dispatcher/PDM共用的session → 局部更新新嵌套表 → 标脏/通知 → `StandaloneSave.Flush()`请求真实落盘。

不要只调 `PDM.FlushImmediate`宣称成功，它当前仅有日志。当前`StandaloneSave`私有writeFile返回boolean，但公开Flush没有转发返回值，因此外部无法直接确认本次写盘成功。未来实施时建议只增加 `Flush → return writeFile()` 的兼容返回，不改变旧写盘流程/防抖策略，并给新层保留dirty/retry状态；旧调用者忽略返回值仍兼容。

错误至少分别覆盖无法打开、WriteString失败、编码失败。测试必须调用实际公开Flush并注入底层File/cjson失败，不只mock Flush返回false；恢复后经真实重试读回内容。编码失败当前不自动安排与开档/写入失败相同的重试，新层必须保留pending-save并按节流策略请求重试。

只有返回true才能提示“已保存”；失败保留内存和可重试，不把“待保存”当永久保存。新层不得为每帧失败无限强制Flush，应借既有防抖与自己的有限节流重试，只在状态边界请求立即保存。

首次解锁可按通关资格建立，但原件在档案中的**可见层级**另由首次处理节点控制：

- E01已解锁可在待阅页提示“夹页待核”，用户点开原件即发起N02/等价首次阅读，处理完成或skip后才开放直接回看。不能只凭资格在后台标finished。
- E02资格由204建立；缺204历史的案件副本，只在N12首次调查资料准备时挂接，不提前伪造玩家获得记录。
- E05资格由4905建立，但初始抄件在N13首次处理后公开；N12尚未处理时，档案只显示“调查待阅”，不可直接跳看印鉴结论。
- E05人员附页在N14首次处理后开放；直接回看不能提前跳过首次依赖。

保存完成前进度可留内存，重启丢失时最多重播该无奖短节点，不会重复发物资。清档递增epoch并取消租约，避免旧回调写回新session。

### 6.5 待播状态

资格、已处理结果持久化；待播队列可由资格＋依赖重新生成，不持久化进程token。

新层每次资格刷新只新增未知项，不清已处理；各节点最多一个待播槽。N12–14总共3短段，重启中断从未完成段重播，不要求整条调查重看。

## 10. 风险、范围守卫与验收标准

### P0风险

1. 用preclaimed当结束历史，会造成“没读过却标完成”。
2. 同步回调show下一段，下一段回调可能被旧清理吞掉。

4. 旧档缺ENTER73，又把73当硬门槛，剧情永久卡住。
5. session整表更新漏字段，损失教程/开场/经济相关状态。
6. 首批只有N02/N12–14，却引用未实现N03/E02或N11，会成为悬空语境。

### 守卫

- 新接口不是引擎API，实施前核对真实代码签名。
- 最小节点都在独立命名空间，运行旧情景原文保持逐字一致。

- 接线前确认只读回看入口；不擅自实现付费入口、经济奖励或新过场。
- 所有schema/模块新增保留meta，构建身份/存档/截图不提交。

### 接线完成的定义

- 两单元四节点在新档与严格已通旧档可进入，skip不锁链，中断可恢复。
- 回看和物证解锁不发任何经济奖励，不伪造已读或真实死亡历史。
